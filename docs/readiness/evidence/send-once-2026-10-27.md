**Status: verified in synthetic testing.** Covers family messages, staff messages and family
requests for a person to follow up. Addresses proposed item PB-19 in
[brief-reconciliation-2026-10-27.md](../../brief-reconciliation-2026-10-27.md) for those three

## In the browser

As Daniel on `/family/messages` (development server, synthetic data), the page's `fetch` was
wrapped so the first send reached the server but its reply was thrown away:

1. The box kept the text and said "We couldn't confirm this was sent…". No copy was shown.
2. "Send message" again sent the **same** submission ID; the live region said "Message sent to your
   care guide." and the box cleared.
3. After a reload the thread held exactly **one** copy of the message.

## Limits

- **Concurrency on a real server:** the embedded database runs one query at a time, so the
  five-at-once test doesn't race. The racing branch is proven by a direct test of `createOnce`, and
  the unique index is proven by a direct insert; a real Postgres run is still needed (PB-09).
- **Scope:** other writes (tasks, consent actions, vault reviews, notes) don't take an ID yet, and
  the app-wide failure message still says "nothing was changed" for them, which may be untrue
  when only the reply was lost. Both are listed for a later increment.
- **No queued or background sending:** if the person closes the page before confirming, nothing is
  retried for them; they see the message on return only if it arrived.
