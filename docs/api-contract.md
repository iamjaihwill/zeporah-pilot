# API contract

The contract between screens and server is the set of TanStack Start **server functions** in [`src/functions/`](../src/functions). They are typed end to end: the browser imports the function, TypeScript knows its input (validated at runtime with zod) and its output. There are no hand-written REST endpoints.

## Conventions

- Every function runs on the server, resolves the session cookie, and rebuilds the actor's context from the database ([rpc.ts](../src/server/rpc.ts)). Nothing in the request is trusted as an identity claim.
- Every function except the session functions in `src/functions/session.ts` returns a `Result<T>`:

```ts
type Result<T> =
  | { ok: true; data: T }
  | {
      ok: false;
      code:
        | "NOT_AUTHENTICATED"
        | "OUT_OF_SCOPE"
        | "NOT_PERMITTED"
        | "INVALID"
        | "CONFLICT"
        | "ERROR"
        | "READ_ONLY";
      message: string;
    };
```

- `message` is always safe to show the person. `OUT_OF_SCOPE` is used both for records that don't exist and for records in another tenant or outside the person's scope, so existence never leaks.
- `GET` functions only read. `POST` functions change state and always write an audit event for meaningful changes.
- Packet release returns a policy decision (below) inside `data`; a hold or deny is a successful _call_ with a refusing _decision_.

## Policy decision shape

```ts
type ReleaseDecision = {
  decision: "allow" | "hold" | "deny";
  reasonCode: ReasonCode; // stable; see src/domain/policy/reason-codes.ts
  explanation: string; // safe, plain language
  auditContext: {
    checks: { check: string; passed: boolean }[];
    packetId: string;
    actorId: string | null;
    evaluatedAt: string; // ISO time
    detail?: Record<string, string | string[]>;
  };
  receiptId?: string; // on allow
};
```

**Submission IDs** (2026-10-27): the three sends above take a `submissionId` the device makes once per send and keeps until the server confirms it. The same ID from the same person returns the first copy (`replayed: true`) without a second audit event or notification; different content under it is refused (`CONFLICT`). Each returns `{ id, sentAt, replayed }`. See [readiness/evidence/send-once-2026-10-27.md](readiness/evidence/send-once-2026-10-27.md).

**Enrollment** (decisions 66–70, 2026-10-27): `getEnrollment` (GET, `household.enroll`: count, cap and care guides), `enrollHousehold` (POST `{ patientName, careGuideActorId }`, `household.enroll`; refused at the cap), `inviteFirstMember` (POST `{ householdId, role: "patient" | "coordinator", name, email, identityConfirmation }`, `household.invite_first`; returns the one-time link once). `getHouseholdOverview` now includes `activation`.
